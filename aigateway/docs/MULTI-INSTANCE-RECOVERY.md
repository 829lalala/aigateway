# 多实例故障恢复设计

本文用于面试讲解和后续改进评估，依据当前代码编写。多实例指同时运行多个后端进程；故障恢复指进程或依赖中断后恢复服务并核对数据。当前未完成双实例故障演练，也未提供生产级高可用部署。

## 当前部署边界

本地 Docker Compose（用配置文件启动依赖容器的工具）只有一个 MySQL 数据库、一个 Redis 缓存和一个 Kafka 消息队列节点。仅 MySQL 显式配置了命名数据卷，也就是容器之外保存数据库文件的位置；Redis 和 Kafka 没有在项目配置中定义持久数据卷，不能依赖删除并重建容器后保留数据。增加后端进程不能消除这些依赖的单点故障。

## 状态放在哪里

| 状态 | 当前存放位置和跨实例行为 | 故障边界 |
|---|---|---|
| 用户、权限、账单、已领取码、死信记录 | MySQL，共享数据库可被多个进程访问 | 数据库故障时关键操作失败；仍需要备份和恢复验证 |
| 登录身份 | JSON Web Token（JWT，携带签名的登录凭证）；实例使用相同签名密钥验签 | 管理操作每次查数据库当前角色；密钥必须一致且不能写入仓库 |
| 应用程序接口密钥（Application Programming Interface Key，API Key）的缓存 | Redis，共享缓存 | 数据恢复时需核对缓存与数据库，不能因缓存存在就认定依赖全正常 |
| 限流桶、秒杀库存和参与用户集合、计费预扣余额 | Redis，共享操作；Lua 脚本在 Redis 内原子执行，即一次执行中不被其他命令插入 | 原子执行不等于与 MySQL、Kafka 一起提交，也不等于故障后自动恢复 |
| 限流配置副本 | 每个进程内缓存，正常情况下约 5 秒后重新读 Redis | 写入实例立即失效，其他实例可能短暂使用旧配置；读配置失败会回退默认值 |
| 模型熔断状态 | 每个进程内存；熔断是持续失败后暂时跳过模型的保护措施 | 各实例独立判断，重启清空，不是统一的上游保护开关 |
| 流式连接与结算回调标记 | 当前进程内存 | 连接不能迁移；进程被强制结束时回调可能无法执行，需要账务核对 |

依据：`HealthController`、`RateLimitConfigProvider`、`RateLimitInterceptor`、`CircuitBreaker`、`ChatService`、`BillingService` 和 `docker-compose.yml`。

## 核心链路的故障窗口

### 礼品码秒杀

当前先写 Redis 参与集合，再原子扣库存，最后异步发送 Kafka。进程在这些操作之间退出，或发送异步失败，可能留下“已参与但未发码”的记录；现有发送代码没有等待确认或对所有异步失败做补偿。不能仅根据接口成功或 Redis 剩余库存判断实际发码完成。

消费者先查询该用户是否已有礼品码，再执行数据库认领。数据库更新可以防止同一个码被同时认领，但 `gift_code.user_id` 是普通索引，查重和认领不是一个原子操作。不同分区、不同记录或恢复重放中的同用户消息若并行到达，仍有重复领取风险。消费者组是共同分担消息的一组消费者；同组内一个分区通常由一个消费者处理，但重平衡（成员变化后的分工调整）及重复投递不能替代业务约束。不要为了扩容给每个实例设置不同业务消费组，否则每个组都会各自处理一份消息。

恢复时先暂停新秒杀与导入，核对数据库已发码记录、Redis 参与用户和库存、Kafka 消费进度及死信。存在在途消息时，不能直接把“数据库未发码数量”覆盖到 Redis 库存，也不能清空参与集合重新放行。恢复确认前不自动补发；同一死信的重试互斥不能保证不同死信对应的同一业务只执行一次。

### 聊天与计费

现有聊天入口仍走 Redis 预扣、上游调用、数据库扣费、Redis 结算。账单唯一约束和数据库事务防止重复扣费，但扣费去重发生在上游调用之后，重复请求仍可能产生多次上游费用；进程在预扣后退出、数据库提交后连接中断、流式结算回调未执行等情况下，两本账可能需要人工核对。相同请求重试应保持相同请求编号和内容，不能把“不重复扣费”解释为“不重复调用模型”。

`BillingService` 还提供持久化处理中账单和冻结金额的方法，以及待核对状态；这些方法存在不代表当前聊天入口已经接入完整恢复流程。故障时先按请求编号核对数据库账单、Redis 预扣和上游用量证据，再决定结算或释放，不凭超时自动退款，不通过删除账单解除重复请求限制。

### 死信保存与人工重投

死信按主题、分区、消息位置唯一保存，重复消费不会覆盖已有状态。保存失败时监听器持续重试，相关分区后续消息会等待；需在 Kafka 消息保留期限内恢复，消息过期或节点数据丢失后无法靠监听器补回。

重投通过数据库条件更新先取得资格，再发送，确认收到后写入 `REPUBLISHED`（已重新投递）。数据库和 Kafka 没有共同的原子提交：发送前后进程退出或确认丢失时，记录可能停留在 `RETRYING`（重试中）。超过 5 分钟的告警只是人工核对提示，不会自动解锁或重发。先确认原操作已结束，再核对消息和业务结果；已重投不代表业务成功。摘要死信目前仅保存、查询，不支持重投。

## 故障后的操作顺序

先限制受影响业务的新请求，保留日志、请求编号和消息位置；再恢复依赖并核对数据，最后小流量验证后恢复入口。限制入口目前需要人工操作，项目没有自动故障切换控制器。

| 故障 | 需要核对和恢复的内容 | 恢复条件 |
|---|---|---|
| 一个后端进程退出 | 将该进程移出请求入口；检查在途聊天、预扣余额、死信重投状态；重启后观察消费者重新分工 | 连接恢复，异常请求有处理记录；不能只看进程重新启动 |
| MySQL 不可用 | 恢复原数据，核对账单提交结果和消费进度；允许死信保存恢复重试 | 数据库可读写、失败记录可解释，消息未因保留期限到期而丢失 |
| Redis 不可用或数据丢失 | 暂停秒杀及需预扣的聊天；核对库存、参与集合、余额和限流配置；明确在途消息后再修复状态 | 共享状态与数据库及在途请求对齐；不要整体清空 Redis 作为恢复办法 |
| Kafka 不可用或数据丢失 | 排查发送确认和业务已受理但未到账记录，恢复原节点数据及消费进度 | 消息可继续消费且缺失范围明确；重建空节点不能算原数据已恢复 |
| 上游模型超时 | 检查上游是否已消费、账单是否落库及 Redis 预扣是否结算 | 请求有可解释结果；不确定消费先保留证据，不能盲目重试或退款 |

`GET /health` 当前总状态固定返回 `UP`，单独报告 Redis 探测结果，不检查 MySQL 或 Kafka。因此接收请求的入口不能只根据总状态放行；至少检查 Redis 字段并另行验证数据库、消息队列和核心读写路径。未来引入负载均衡器（把请求分发给不同实例的入口）时，需要先补齐适合接流量的健康判断。

## 双实例演练设计：尚未执行

只在可重建的独立测试环境演练，使用同一版本、相同登录签名密钥及同一套依赖，后端监听不同端口。当前 Compose 的 Kafka 公布地址为 `localhost:9092`，适合宿主机启动后端；直接把后端放入另一容器需要调整消息队列地址，不能直接照搬配置。

| 场景 | 将来演练要观察的结果 |
|---|---|
| 同一登录凭证分别访问两个实例 | 身份一致；普通用户都不能调用管理接口，角色撤销后两个实例都拒绝管理操作 |
| 同一死信并发请求两个实例重投 | 只有一个取得数据库资格；其他请求冲突；发送确认和业务结果分别核对 |
| 停止其中一个实例 | 新请求只进入存活实例；消费者完成重新分工；中断的流式连接明确失败，不能伪装已迁移 |
| 更新限流配置 | 修改实例立即重新读取，其他实例正常情况下约 5 秒更新；共享桶不因增加实例扩大配额 |
| 重复请求及故障时的账务 | 数据库无重复扣费，Redis 余额核对一致；单独记录可能重复的上游调用，不能只查账单 |
| 同用户多条礼品码消息 | 核对用户最多领一个码；目前缺少数据库业务约束，应先补强再声称支持并发恢复 |

已有证据包括单元测试、真实数据库集成测试及一次真实 Kafka 死信重投和重复消费演练；数据库条件更新的并发测试不是两个完整实例的故障切换演练。指标、告警接口也只按管理员请求计算，没有定时采集和主动通知。

## 后续若确需部署，优先补什么

先补数据库业务唯一约束及故障后的账务核对闭环，再完善接流量健康判断、依赖持久化与备份恢复，最后验证上述双实例场景。需要可靠衔接数据库与消息队列时，可评估事务发件箱（Transactional Outbox）：业务数据与待发送事件在同一数据库事务中保存，再由发送任务投递；它仍需消费者防重复处理，并非消息自动只处理一次。本文仅记录方向，当前没有实现发件箱、自动账务恢复或依赖集群。

面试表述：“项目已完成单实例业务演示、数据库重投互斥和真实死信重投验证；能够指出跨系统提交与本地状态的故障窗口，多实例恢复目前有设计说明，尚未完成部署与故障演练。”
